# Dream Map 产品与体验评估

日期：2026-09-30。范围：UI 与交互、地图显示、实体字段、产品吸引力。

## 主要判断

Dream Map v0.1 已具备“看见梦想 → 发布梦想 → 支持梦想 → 更新状态”的基本流程。现有深海蓝地图、奶油白面板、珊瑚色按钮值得保留，梦想者所在地与梦想目的地分开也很合理。

下一阶段最值得投入的是：让地图更容易探索、让卡片更能讲述真实的人、让帮助真正有后续。建议定位为 **“发现与你有共鸣的梦想，帮助彼此迈出下一步”**。地图负责发现与空间联系，故事和进展负责共鸣与回访。

本报告区分源代码能够确认的问题与待验证的产品假设；新增字段和布局尺寸均为建议，不代表已经实现。审阅入口：`app/page.tsx`、`app/globals.css`、`lib/dream-data.ts`、`db/schema.ts`、`app/api/dreams/route.ts`。

验证范围：安装锁定依赖、本地构建通过、初始化独立的本地数据库，在本地浏览器检查默认视口、1440×900 桌面和 390×844 手机页面。检查筛选、地图点点击、列表打开详情、键盘打开地图点、创建表单；没有向线上写入数据，也没有实测大量数据性能。项目业务代码未修改，仅新增此评估文档；本地安装、构建与预览数据位于忽略目录。

实际复现：选择 Achieved 后列表为 2 张卡，地图仍有 12 个标记。点击 Jakarta、Shanghai 地图点均未打开详情；点击列表卡片正常，Shanghai 点按 Enter 也能打开详情。地图点击问题应优先修复，具体原因还需在修复时定位。1440px 桌面地图宽度实测 700px，但加载全部示例后地图高度达约 2638px，超过 828px 的可用高度，地理轮廓落在首屏下方；中等宽度也复现网格行溢出。

## UI 与交互

### 1. 首屏让地图成为视觉中心

现状：桌面三栏常驻，左侧最大 360px，右侧最大 380px；即使没选梦想，右侧仍用整栏展示介绍。1440px 宽时地图只剩约 700px。世界轮廓本身约为 2:1，竖长容器使其上下产生大量空白。

**应先修复高度溢出。** 本地页面中，`.workspace` 本身受屏幕高度限制，但默认网格行仍被探索列表的最小内容尺寸撑高。1440×900 加载 12 条示例后，地图实际高约 2638px；整个 app-shell 又隐藏溢出，导致首屏大面积空白、地图主体和底部工具落到视野外。优先检查 `grid-template-rows: minmax(0, 1fr)`、`.explore-panel` 与 `.list-scroll` 的 `min-height: 0`，使列表只在自己的容器内滚动。修复后再调整地图比例和布局。

建议：默认显示 300–320px 的探索栏与剩余宽度的地图；把介绍压缩为地图内的小型欢迎卡。选中梦想再展开 340–380px 详情，关闭即归还地图空间。在中等宽度下，详情可以覆盖地图，但地图视角需要为遮挡区域留出安全边距，让选中点始终可见。具体尺寸应以原型验证。

### 2. 手机保持地图和内容之间的上下文

现状：手机地图、表单、列表纵向排列；详情使用固定侧面板；创建时通过页面滚动往返地图与表单。

建议：地图作为主画布，列表采用可收起的底部面板，点击梦想展开底部详情。增加“地图 / 列表”切换，让不方便操作地图的用户也能完整浏览。定位流程独立为“搜索城市 → 预览位置 → 确认”，结束后返回表单的同一位置。

底部层需支持关闭、Esc、焦点转移与恢复。若采用模态模式，要限制焦点进入背景并使用正确的对话框语义；若允许继续操作地图，则应明确采用非模态设计。[W3C 对话框交互模式](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)

### 3. 卡片显示人与行动

现状：卡片以状态、标题、描述、地点、名字和票数为主，头像只有详情里的姓名首字母。

建议卡片信息顺序：

1. 可选封面或分类小插画，加头像与城市；无图片时提供漂亮的文字卡。
2. 梦想标题和一句动机。
3. “下一步：完成第一版作品集”等具体行动。
4. “需要：设计反馈 / 引荐 / 一起练习”等帮助标签。
5. 最近进展、支持数与状态。

不是每张卡都需要大图。可以只为精选梦想展示封面，以免列表过长或内容质量参差。颜色继续代表进度，图标或封面代表分类，避免同一套颜色表达两种含义。

### 4. 探索入口更明确

现状：只支持视野内文本搜索与状态筛选，列表固定按创建时间倒序。搜索不含目的地文本；拖动地图会立即改变结果。

建议区分“搜城市”与“搜梦想”，明确全世界和当前区域两个范围。全球搜索结果点击后定位到地图；区域搜索保持区域限制。增加“最近更新 / 需要帮助 / 与我相关”入口，分类先控制在少量清晰主题。

地图移动时先保持列表稳定，在结束移动后更新，或用“搜索此区域”按钮由用户确认；选中梦想在筛选结果外时，保留独立的选中标记并提示。列表悬停高亮地图点，点击地图点把对应卡片滚入视野。

### 5. 创建与反馈减少困惑

现状：必须先点地图才可发布；没有城市搜索、草稿持久化、编辑梦想或“我的梦想”入口。`draft` 仅保存在页面状态，刷新会丢失。错误与成功均使用同一绿色提示样式。未登录时操作失败后显示错误，但没有明确的登录引导。

建议：首步只填写标题和城市，分类、动机、目的地、图片和帮助需求渐进补充。城市搜索与地图微调并存；默认显示到城市级。用会话内草稿或清晰标注的本地草稿保存，发布成功后提供“查看我的梦想”和“分享”。补充编辑、归档与更新进展入口。

支持按钮使用“为 TA 加油 / 已加油”更符合产品语气，但它的计数应与收藏、关注分开。成功、失败、加载分别设计反馈；操作期间只锁定相关按钮。`reload()` 当前吞掉刷新错误，POST 成功后仍可能显示成功而数据未更新，应明确提示“操作已保存，显示刷新失败”。

## 地图显示与交互

### 已确认的实现问题

| 问题 | 代码依据 | 建议 |
| --- | --- | --- |
| 桌面地图和探索面板被内容撑到屏幕以下 | 默认 grid auto 行与子项 min-height；本地 DOM 高度实测 | 限制网格行，子面板允许收缩，列表内部滚动 |
| 筛选只改变列表，地图仍绘制全部点 | `visible` 在 `page.tsx:73` 计算，地图在 `page.tsx:158` 使用 `dreams.map` | 拆分 `filteredDreams` 与 `viewportDreams`，地图、列表和计数共用一致的筛选规则 |
| 点大小随容器宽度变化，手机上过小 | 半径仅除以 `zoom`；初始视野宽 1000 | 按实际屏幕像素换算可视半径与透明点击区域；保持命中区域足够大 |
| 每个国家固定放大 2.2 倍 | `selectCountry` 使用中心与固定倍率，`page.tsx:93` | 按国家投影边界与实际可用画布拟合，并留面板与标签边距 |
| 缩放围绕画布中心，无法保持鼠标指向的地点 | `wheel` 只改变 zoom，`page.tsx:132` | 缩放同时补偿 center；支持触控捏合与连续触控板滚动 |
| 多指状态未管理 | 拖动仅有一个 `drag` 引用，`page.tsx:115` | 跟踪 pointerId 与多指，或使用成熟缩放行为 |
| 同城梦想完全重叠 | 每个梦想直接投影到地点，无聚合 | 世界视角显示数量簇，城市视角再展开点；完全同坐标可展开小列表 |
| 目的地没有单独标记 | 选中梦想只绘制 `<line>` | 为目的地绘制不同形状与名称；提供“查看完整旅程” |
| 旅程直接连屏幕直线 | `page.tsx:158` 使用 `<line>` | 用地理 LineString 绘制球面连线，正确处理日期变更线 |
| 国家路径在各种状态变化时反复计算 | 每次渲染均执行 `path(c)` | 固定投影时预计算国家路径，独立底图组件，移动动画按帧处理 |
| 分享链接不自动定位梦想 | 初始 URL 只设置 selectedId，`page.tsx:58` | 数据加载后定位选中梦想；缺失 ID 展示明确状态 |

按当前布局与投影计算，390px 宽手机的光点实心直径约 5.1px，外圈约 10.9px；1440px 桌面实心约 9.1px。除以 zoom 只能抵消放大，不能抵消不同容器的像素比例。建议手机命中范围以 40–44px 为设计目标，密集区域由聚合解决；这是产品建议，不能据此直接判定 WCAG 不合规，因为标准还包含间距和等效控件例外。[W3C 目标尺寸说明](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum)

在当前底图上做了投影计算：日本投影宽约 44.8 单位，而固定国家视野宽约 454.5，国家只占视野宽约 10%；俄罗斯跨日期变更线，原始投影包围盒宽约 1000。国家拟合需要处理跨界、海外领土与主体区域，不能直接对所有坐标做一次普通 min/max。D3 提供投影拟合与路径边界接口，可作为实现基础。[D3 projection](https://d3js.org/d3-geo/projection)、[D3 path.bounds](https://d3js.org/d3-geo/path)

本地已复现地图点鼠标点击不打开详情，但列表点击和地图点键盘 Enter 正常。`startDrag` 在 pointerdown 即捕获到 SVG 祖先，可能影响子元素收到 click，是优先调查的原因；根因尚未通过修复验证。建议到确认发生拖动时再捕获，或统一在地图层进行点与国家命中判断，并覆盖点击、拖动后松手与触屏测试。另外，SVG 整体的 `role="img"` 可能使内部交互点的可访问性语义被弱化，本地可访问性树未列出这些点；应调整整体语义并保留列表作为完整探索入口。

### 地图层次与审美

保留暗色海洋与温暖的梦想光点，弱化经纬网；世界视角主要呈现大陆、梦想簇和少量地区名。国家视角补充国家/城市名；城市视角展开梦想。选中点采用明确的光圈和名称卡，脉冲只用在当前选中或最新进展，尊重减少动态效果的偏好。

不要依赖放大粗略的 110m 国家轮廓提供精确城市导航。全球概览可以继续使用 D3；若城市浏览成为核心任务，再比较 MapLibre 的矢量底图、内置聚合与平移缩放。还需单独确定底图来源、地名搜索、覆盖范围、服务成本与地图署名。地图引擎本身不会提供完整的地点搜索服务。[MapLibre 聚合示例](https://maplibre.org/maplibre-gl-js/docs/examples/cluster/)

### 数据增长前的准备

当前 GET 拉取所有梦想，每次还执行 24 条示例插入语句；支持、帮助、改状态后会再拉取全量。对 12 条样例尚可，不代表已测到性能瓶颈。

建议把示例初始化移到迁移或一次性种子流程；地图摘要与详情拆开；列表支持分页、状态/分类筛选和视野查询。处理跨日期变更线的视野条件，移动结束后再请求并取消过时响应。现有经纬度联合索引的实际收益需要用真实查询与查询计划验证。先用真实数据量和较弱手机测量交互延迟，再决定 Canvas 或 WebGL。

## 实体与字段

当前四个实体：`dreamers`、`dreams`、`votes`、`help_offers`。优点是支持票唯一约束已经存在，梦想与用户分开，所在地必填、目的地可选。建议保留其简洁性，按交互需求逐步扩展。

| 实体 | 第一阶段建议字段 | 解决的问题 |
| --- | --- | --- |
| Dreamer | `display_name`、`avatar_url`、可选 `bio`；后续 `skills`、`languages` | 认识具体的人、匹配可提供帮助；昵称由用户设置，避免直接以邮箱前缀作为展示身份 |
| Dream | `category`、`updated_at`、`next_step`、可选 `target_date`、`visibility`；后续可选封面、达成说明 | 分类探索、看到下一步、按最近进展排序、控制公开范围 |
| Dream location | `country_code`、`city`、`place_id/provider`、`precision` | 稳定筛选与城市选址，不依赖可自由修改的地点名称 |
| Dream need | `dream_id`、`type`、`description`、`status` | 明确需要技能、建议、资源、引荐或同行者；一个梦想可以有多项需求 |
| Dream update | `dream_id`、`body`、可选媒体、`created_at` | 时间线、回访与真实进度；初期可不单独做里程碑实体 |
| Help offer | 可选 `need_id`、`type`、`status`、`updated_at`、接收方已读时间 | 从留言变为“待回应 → 已接受 → 已完成 / 已婉拒”的流程 |
| Follow | `user_id`、`dream_id`、`created_at`，组合唯一 | 回访、关注进展；与加油票语义区分 |

字段取舍：

- **分类与标签分开。** 少量固定分类用于导航，多标签用于表达。现有单一 `hashtag` 可逐步迁移为标签关联，不必一开始增加复杂推荐系统。
- **不强制虚构完成百分比。** 学习、创业、社区项目的完成尺度不同。先有状态、下一步、进展记录；适合量化的梦想再提供里程碑。
- **位置归属要说清。** 用户当前城市属于个人资料；梦想的出发城市属于梦想创建时的快照。用户搬家不能自动改写旧梦想的起点。公开点默认城市中心；不需要精确住所就不采集。
- **目的地继续可选。** 它表示地理目标；“成为插画师”等非地理目标使用梦想描述、下一步与分类表达。
- **生命周期与公开范围分开。** 保留 `dreamed / in-progress / achieved`；需要暂停时增加相应状态，归档使用单独字段。个人草稿和公开梦想不要仅靠状态颜色区分。
- **计数继续视为派生值。** votes、helpCount 初期从关联记录计算；只有实际测到查询压力再引入缓存，并定义一致性规则。
- **关联帮助保持私密。** 当前帮助正文仅向梦想者和帮助者返回，这一边界合理。公开可显示经同意的感谢或达成故事。
- **约束与操作同步设计。** 状态、坐标范围、目的地三字段同时为空/完整等应有一致的校验；补充编辑、取消、归档与帮助状态转换权限。

建议第一版只增加分类、下一步、更新时间与城市标识，再做进展记录和帮助状态。发布表单仍以“标题 + 城市”作为最小输入，其余在发布后补全。

## 产品吸引力

### 首屏表达

可以尝试“世界上，有人正在实现与你相似的梦想。”副句解释能做什么：“找到同路人，为一个梦想加油，或帮 TA 迈出下一步。”主操作“把我的梦想点亮”，次操作“发现一个有共鸣的梦想”。这组文案属于待测试方案。

世界地图要在首屏清晰可辨；用一张精选梦想小卡展示人物、下一步与具体帮助入口。现有 `A WORLD OF POSSIBILITY` 与指南式介绍可以缩短，释放地图空间。

### 三个值得测试的特色

1. **寻找同路人。** 按城市与分类连接相似目标的人，先用规则匹配；展示匹配依据。
2. **下一步，而不是宏大口号。** 列表可直接看到一个近期行动和可参与的帮助；进展更新后关注者能发现变化。
3. **梦想旅程与达成故事。** 有地理目的地时呈现起点到目的地的弧线；无目的地时呈现从想法到行动的时间线。达成后提供可分享的成果卡与经允许展示的感谢。

不建议第一阶段投入全屏 3D 地球、复杂排行榜或强制 AI 生图。先验证浏览、发布、匹配与回应。可以把“随机发现一个梦想”作为低成本探索入口，但推荐范围与筛选应一致。

### 冷启动与信任

现有 12 个 Example 标记是好的基础。建议示例能单独筛选，并在示例的帮助入口明确说明没有真实接收者。真实梦想与示例不应混算活跃人数、达成数或有效帮助。早期按少量真实主题策划内容，精选“正在做什么、缺什么、发生了什么变化”的完整故事，比堆积空点更有吸引力。

### 分享与回访

已有 `?dream=id` 分享状态，但没有分享按钮，打开链接也不自动定位。先补“复制链接”、直接打开并定位梦想、分享后保留当前视角或适合该梦想的视角。再做人物/主题/城市/下一步组成的分享图片与逐梦想预览元信息；当前页面元信息是全站统一的。

帮助提交后让双方知道下一步；增加“我的梦想 / 我关注的 / 我提供的帮助”统一入口。通知先聚焦实际帮助与被关注梦想的重要更新，避免每次点赞都打扰。

## 验收与衡量

先验证以下场景：状态筛选后点与卡片一致；同城多梦想均可选；地图拖动后不误打开详情；打开分享链接自动定位；手机创建过程中不丢草稿；未登录用户能理解如何继续；帮助者提交后、梦想者打开后都能看到清晰状态。

视口建议覆盖 390×844、768×1024、1280×900、1440×900、1920×1080；输入覆盖鼠标、触控板、触屏、键盘。地图性能用真实密度数据和较弱设备测量，不根据点数直接承诺帧率。

产品指标：首次会话打开真实梦想的比例、创建完成率、城市选址耗时、有效帮助回应率、关注后的回访率、分享带来的详情访问。均排除示例与本地测试数据，先建立基线，再判断改版是否有效。
